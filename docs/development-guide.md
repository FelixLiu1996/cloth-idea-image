# 开发规范

## 1. 基础原则

- 先明确验收条件，再实现功能。
- 业务规则优先放在领域层，不堆积在页面或路由处理器中。
- 平台差异和模型差异通过适配器隔离。
- 小步提交，每个提交只表达一个清晰意图。
- 不以临时演示代码替代正式错误处理、安全和测试。

## 2. 运行环境

- Node.js 20 或更高版本。
- 正式应用初始化后统一使用仓库锁定的 npm 版本和 lockfile。
- TypeScript 开启 `strict`、`noUncheckedIndexedAccess` 和 `exactOptionalPropertyTypes`。
- 统一使用 UTF-8、LF 和文件末尾换行。

## 3. 命名与目录

- 文件与目录：`kebab-case`。
- React 组件、类型、接口：`PascalCase`。
- 变量、函数、Hook：`camelCase`。
- 常量仅在真正不可变且跨模块表达配置时使用 `UPPER_SNAKE_CASE`。
- 测试文件与源文件同名，使用 `.test.ts` 或 `.test.tsx`。
- 禁止使用 `utils.ts`、`helpers.ts` 等无限扩张的通用文件；按领域命名。

## 4. TypeScript

- 禁止无理由使用 `any`；外部输入先视为 `unknown` 并校验。
- 导出的函数、Provider 和领域对象必须有明确类型。
- 使用判别联合表达任务状态和错误，不依赖魔法字符串。
- 不使用非空断言掩盖数据问题。
- 环境变量集中读取、校验和转换，业务代码不得到处访问 `process.env`。

## 5. React 与 Taro

- 页面组件负责组织，领域 Hook 或服务负责业务逻辑。
- 不在渲染期间发起请求或产生副作用。
- 上传、登录、保存图片、分享和导航通过平台适配层实现。
- 样式优先使用跨端支持良好的布局能力；平台专属样式单独隔离。
- 每个异步页面至少处理加载、空数据、失败、重试和防重复提交。
- H5 功能完成后，必须检查是否引入未隔离的浏览器专属 API。

## 6. 服务端

- 路由层只处理协议转换、鉴权、校验和响应。
- 用例层编排业务，Provider 层处理厂商协议。
- 外部请求必须设置超时，并记录请求 ID、Provider、模型、耗时和结果状态。
- 不自动重试参数错误、内容安全错误或余额不足。
- 可能重复计费的请求必须使用幂等键。
- 厂商返回的临时结果 URL 必须及时下载并转存。

## 7. 错误规范

业务错误至少包含：

- 稳定错误码。
- 用户可理解的信息。
- 是否允许重试。
- 内部可追踪的请求 ID。

推荐错误码前缀：

- `UPLOAD_`：上传与文件问题。
- `VALIDATION_`：输入校验问题。
- `GENERATION_`：生图任务问题。
- `PROVIDER_`：模型厂商问题。
- `AUTH_`：会话和权限问题。
- `RATE_LIMIT_`：额度与频率问题。

禁止把堆栈、Key、Authorization、完整厂商响应或内部路径返回客户端。

## 8. 日志与隐私

允许记录：

- 任务 ID、会话 ID 的不可逆或内部标识。
- Provider、模型、提示词版本、耗时和状态。
- 厂商请求 ID 和标准化错误码。

禁止记录：

- API Key、Cookie、Authorization 请求头。
- 完整 Base64 图片。
- 带长期签名的私有资源 URL。
- 未经处理的个人信息和用户隐私输入。

## 9. 测试策略

- 领域规则：单元测试。
- Provider 请求构造与响应转换：契约测试和固定样例。
- 服务端路由：集成测试。
- 上传到结果展示的关键流程：端到端测试。
- 真正调用付费模型的测试默认不进入普通 CI，使用显式命令和预算限制。
- 模型效果测试必须记录模型、提示词、参数、耗时、成本和评分。

## 10. Git 与提交

提交信息使用以下前缀：

- `feat:` 新功能
- `fix:` Bug 修复
- `refactor:` 不改变行为的重构
- `test:` 测试
- `docs:` 文档
- `chore:` 工程与依赖

提交前检查：

1. 工作树中没有密钥、用户图片或调试输出。
2. 格式、类型检查和相关测试通过。
3. 文档和变更记录按需更新。
4. 提交内容围绕一个明确目的。

## 11. 文档更新规则

| 变化类型 | 必须更新 |
|---|---|
| 用户可感知功能或行为 | `CHANGELOG.md`、相关产品文档 |
| 当前进度、阻塞、下一步 | `docs/current-status.md` |
| 模型、参数、提示词或效果测试 | `docs/model-evaluation-log.md` |
| 架构或不可轻易逆转的决定 | `docs/decisions/` 新增 ADR |
| 环境变量 | `.env.example`、README 或部署说明 |
| 公共 API/数据结构 | 架构文档和契约测试 |

不需要为纯格式化、错别字或不改变行为的局部重命名单独写变更日志，但 Git 提交仍应清晰。

## 12. Definition of Done

- 验收条件实现且可复现。
- 正常、失败、空状态和重复操作得到处理。
- H5 与跨端约束经过检查。
- 安全、隐私和调用费用风险经过检查。
- 相关测试通过。
- 文档与记录已同步。
