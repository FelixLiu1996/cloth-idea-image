# 0006：使用可轮询的异步生图任务

- 状态：Accepted
- 日期：2026-08-27

## 背景

生图通常需要十几秒或更久。同步上传请求必须一直保持连接，移动网络中断、浏览器超时或用户切换页面后，客户端难以判断服务端是否已经触发付费调用；如果直接重新提交，还可能重复生成和计费。继续修改与首次生成有相同问题。

服装分析当前约需四十秒，但分析结果尚未持久化。本轮优先解决付费更高、已有任务实体和结果状态的生图路径，避免一次同时改动全部接口。

## 决定

1. 首次生成、再次生成和继续修改先创建任务，首次提交返回 HTTP `202`、`jobId` 和 `statusUrl`。
2. 客户端通过 `GET /api/v1/generations/:jobId` 查询 `queued`、`generating`、`succeeded` 或 `failed`。
3. Provider 成功后立即转存临时结果，再将任务标记为 `succeeded`；标准化 Provider 错误保存为 `failed` 终态。
4. `Idempotency-Key` 从任务创建开始绑定请求指纹和任务 ID。提交传输失败时，客户端只用同一键重试一次；Provider 失败不自动重新生图。
5. 当前使用进程内任务仓储和执行器完成产品验证，后续保持 API 和领域状态不变，将实现替换为数据库、队列与独立 worker。
6. 分析接口本轮继续同步；在分析记录和原图引用具备持久化方案后再迁移。
7. 当前不提供取消。厂商调用能否中止、已经产生的费用以及 worker 回收语义明确后，再增加取消状态和接口。

## 原因

- 上传连接结束后任务仍能完成，客户端可以恢复短暂的查询网络错误。
- 提交重试复用同一任务，降低重复付费风险。
- 排队、执行、成功和失败可观测，客户端不再用一个长连接猜测任务状态。
- 先保持现有 H5 业务 API 的成功结果类型不变，页面逻辑只需等待服务层轮询完成。
- 进程内实现足以验证接口边界，又不会把临时队列方案写死在业务层。

## 影响

- 当前任务、幂等记录和父子关系只存在于单个服务进程，重启后任务状态丢失，也不能支持多实例；这不是可公开部署的正式异步基础设施。
- H5 当前页面可自动轮询并容忍短暂网络失败，但没有跨刷新任务索引，轮询总预算结束后只能提示用户稍后查看。
- 受控真实用户试用前必须接入持久化任务库/队列、worker 租约与超时恢复、对象存储、匿名会话、跨刷新历史、清理和限额。
- 状态查询响应禁止缓存；失败终态通过 HTTP `200` 返回嵌套的稳定业务错误，提交校验错误仍使用对应的 HTTP 错误码。
